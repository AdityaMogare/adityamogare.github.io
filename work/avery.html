Intro

Avery handles insurance claims calls. The hard part isn't sounding helpful; it's following a standard operating procedure exactly: verify identity before disclosing anything, get consent before talking to a representative, never promise an outcome, and hand off to a human at the right moment, while still handling callers who are frustrated, off topic, or trying to talk their way past the rules.

Every decision the agent makes is visible next to the conversation: the current SOP phase, the identity gate, what it remembered, which guardrails fired, and a full event trace.

Problem

A free-form LLM will skip verification if asked nicely, invent commitments, and drift off script. In claims support, each of those is a compliance failure.

✎

Solution

The SOP is explicit phases and gates; answers come only from cited guideline facts, and a verifier checks every turn.

✦

Results

46 runnable specs (16 core SOP, 30 edge cases) that anyone can run from the live app, with or without an API key.

For reviewers

Try it in a minute

No API key is needed: without one, the app runs in offline mode with templated, grounded responses. Add an OpenAI, Gemini, or OpenRouter key at the top to use a live model.

  1. Open the live app, click Demo test case, then Send. Watch the SOP phase and identity gate update on the right.
  2. Click Injection and send it. The agent refuses to change its rules, and the guardrail counter ticks up.
  3. Click New session, then Wrong DOB or Representative to see the gate hold.
  4. Open Test cases and press Run on any spec to check it against its expectations.

Architecture

The SOP as phases, not a prompt

Instead of asking the model to remember a procedure, the procedure is the structure. A call moves through four phases, and each turn records the state transitions it caused (for example VERIFIED → CASE_SELECTED → ANSWER_CASE).

Verify IDidentity gate → Resolve intentwhich claim, which question → Process casegrounded answer → Post processsummary email, handoff

Memory crosses phase boundaries: an intent stated before verification ("I'm calling about my denied claim from January") is stored and used afterwards instead of asking again.

Key decision

Nothing is disclosed until the gate opens

Callers verify with any three of full name, date of birth, phone, email, or the last four digits of an SSN or national ID. Claim access stays blocked until they do.

  • Three distinct failed attempts lock verification and transfer to a human, with no hint about which field was wrong.
  • An authorized representative can verify the policyholder, but claim data stays gated until the policyholder's consent arrives. If it never does, the call escalates without disclosing details.
  • A caller who knows the policyholder's details but isn't an authorized representative gets nothing.
  • A verified caller asking about someone else's claim ID gets neither a confirmation nor a denial.

Key decision

Answers come from cited facts, then get checked

Each response is built from the guideline facts available for that case, and the UI shows exactly which facts the responder could use and which ones it cited. A verifier checks every turn and marks it pass or fail. Answers are tagged grounded, so a reviewer can tell at a glance whether a sentence came from the record or from the model.

Guardrails are counted, not just applied: off-topic attempts, injections, and frustration each have a counter, and repeated off-topic pushback eventually leads to a human-transfer offer.

Proof

46 specs, each traced to why it exists

The test cases live in fixtures/specs/scenarios.json and run from the app itself: Run sends every turn in a fresh session and checks the spec's expectations and trace properties; Step sends one turn at a time.

The 16 core specs cover the SOP. The 30 edge cases are tagged with the guardrail they protect and where they came from: findings from live evals, simulated-user evals (including an angry persona), UI review, and the requirements doc.
