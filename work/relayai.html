Intro

Banks run a lot of old software that has no API. The only way in is the screen a staff member uses. RelayAI gives an AI agent hands for those systems.

It works in two halves. A language model drives the real screens once and works out how to do the job. What it learned is saved as a file, and from then on that file does the job with no model involved at all.

Problem

Running a model on every transaction is slow, costs money every time, and can do something slightly different twice in a row. None of that works inside a bank.

✎

Solution

Discovery records the job into a hashed JSON capability a person can review. Replay runs that file with zero model calls, and risky steps wait for a human.

✦

Results

A dispute that takes a rep about 6 minutes by hand replays in 4.3 seconds for $0, with 50 of 50 runs passing.

Architecture

Two halves, joined by one file

Discovery runs an observe, decide, act loop with the model and compiles what worked into a capability file. Replay loads the same file, verifies its hash, then runs governance, input validation, an idempotency check, tenant overlays, and preconditions before each step.

Discoveryonce · 17 s · $0.09 · 13 model calls → capabilities/X.jsonsha256-hashed, reviewed by 2 people → Replayevery run · 4 s · $0 · 0 model calls → Legacy bank UIdefault-deny route allowlist

Everything left of the file happens once. Everything right of it happens in production. The file is the only thing that crosses.

I made the recording data, not generated code. A JSON contract can be reviewed in a pull request, read by a calling agent at run time, and upgraded by a migration. A generated Playwright script gives none of that; you'd be diffing a script instead of a contract.

Key decision

Replay never calls a model, full stop

The value of the project is that production is cheap, fast, and repeatable. A model in the replay path gives all three back.

I considered a small, bounded model retry when a step fails, and I wanted it. The cost of saying no is real: a tiny UI change that a model could shrug off now forces a re-recording. I'd revisit it only as a separate, labelled mode that is never the default and logs every firing.

Key decision

Find controls the way a screen reader does

Legacy bank screens have no automation IDs, and their markup changes for reasons unrelated to meaning (element IDs like ctl00_ctl32_dgAcct_ctl04_lblVal change on every load). So every control is found four ways, best first: accessibility role and exact name, then label, then visible text, then CSS.

The second reason matters more: falling back is a signal. A run that only succeeds on the CSS fallback isn't healthy, it's a warning. Drift detection came out of this almost for free.

Safety

When a person has to decide

Irreversible steps, like confirming a new account or filing a dispute, pause for a human in the same browser session:

  1. The browser stops on the confirm screen with a red banner and session ID.
  2. The operator page shows why it stopped, with a screenshot.
  3. A teller claims it and clicks Confirm themselves, in that same window.
  4. Automation re-observes, sees the work is done, and does not click again.

If nobody claims it within two minutes, the run is abandoned and the button is not pressed. Around that sit a default-deny route allowlist (the agent physically can't reach /admin/wire), a cap of 30 runs per capability per hour, vault references instead of passwords, and customer values redacted from logs by name.

Portability

One recording, several institutions

Credit unions often run the same vendor product with different wording. A capability recorded once against one tenant runs on another with a few lines of YAML instead of a new recording:

# overlays/tenants/tenant-14.yaml
copy:
  Search: Find Member
  Member Lookup: Find a Member
  Confirm: Submit Request

Overlays can rename controls and add error screens, but they cannot change which steps are dangerous. Risk is re-checked after the rename, because the whole point of "Confirm" becoming "Submit Request" is that it's still the dangerous button.

Proof

Numbers you can rerun

There's no real bank to test against, so the repo ships a deliberately awkward fake one: changing element IDs, a legacy frameset, a 90-second login timeout, popups, flaky 503s, and three visual skins. npm run verify runs 27 scenarios in about 40 seconds with no API key.
